# 订阅与版本规则

## 安装与更新

将 README 中的主订阅、扩展订阅地址添加到 VeneraX 或 Venera-Next 的漫画源仓库管理。客户端可同时保存多个仓库；索引 URL 是源列表，不是单个 JavaScript 文件。

从订阅仓库安装并保留仓库关联，客户端才能按仓库索引解析固定 Git 提交的下载地址。直接导入、未关联仓库或旧版客户端可能改用源文件自身的 `url`；部分上游将它指向站点首页，届时请从订阅列表重新导入。

## 收录条件

两份订阅均要求同一轮真实通过核心阅读链路：搜索、发现或分类入口至少一项，详情、章节、实际图片下载及解码。主订阅另外要求整次状态为 `passed`；扩展订阅允许核心链路以外的能力失败或受限。

每个源仅抽查固定样本中的一页和一张图片。结果不保证所有漫画、章节、地区、用户账号、设备或 Flutter UI 均可用。跳过、未触发和缺少凭据不会算作通过。

## 官方版本与重复 key

直接来自 `venera-app/venera-configs` 的官方源码和转引不进入订阅。沿用官方 key 的社区改版仅在版本严格高于官方基线、且自身通过原收录标准时才可收录。版本按三段数字比较；无法解析、相等和低于基线都排除。每轮更新基线只增不降，发布前再次核对官方索引。

订阅内部每个 key 只选一个通过门槛的构建，以避免客户端导入和更新冲突。同 key 社区升级源仍可与客户端内置官方源并存，作为替代版本。

## 同名与同 key 去重

`monitor/catalog.json` 是审阅过的清单，同一站点被不同作者或不同版本重复登记时会累积成多份。每轮巡检前按下面的规则只保留一份，清单因此保持"一个站点一个构建、一个 key 一个构建"：

1. **字节完全相同**：同一源码出现两次（仅仓库不同）只留第一条。
2. **同一个 key**：只保留发布时会被选中的那份。排序与发布一致——今日状态（`passed` > `partial` > 其它）> `priority` > 版本；这个顺序保证删掉的一定是本来就不会进订阅的构建。
3. **不同 key 但同名**：保留排序最高的那个 key，其余同站点的构建合并过去；`KadishJoey/venera-json` 的 `source_xx_hash` 自动导出条目无论排序如何都合并到同名的手写源。

4. **同站不同写法**：名称不同但源码头部请求的是同一个站点域（`www.x.com`、`m.x.com` 视为同站）时，同样只保留排名最高的一份。这条按站点判断而不是按名字，因此能覆盖「漫画柜／漫畫櫃」「X漫画／x漫画-M」这类简繁与移动版命名差异；以下情况不合并，因为它们是不同用途：
   - 多账号版本（`copy_manga_multi_accounts`、`komiic_multi`）
   - 私人部署或重制实现（`hj_baozi`、`baozi_recode`）
   - 同域下的分区源（`fourkhd_cosplay` 与 `fourkhd`）
   - 区域／语言版本（`WEBTOON`、`webtoon移动版`、`Webtoon_us`、`LINE WEBTOON`）
   - 源码指向同一域但站点不同的误判（`六漫画` 与 `喵趣漫画` 共用 CDN 域 `bzcdn.net`）

例外：`monitor/focus.json` 里明确列出的重点复测构建即使与同 key 的其他构建重复也保留——重点复测跟踪的是那份固定构建，删掉会让报告失去证据。当前只有 `ccc` 属于这种情况（`zakkida` 的 1.0.2 供重点复测，`handahao666-boop` 的 1.0.1 供订阅）。

被合并的构建不会出现在订阅里，也不会再占用巡检时间；它们的来源和理由记在合并时的提交说明里。

源备注写在索引 `description` 中：一般写 `引用源：owner/repository`；BB-CHICKEN `jm` 使用固定源码提交对应 CHANGELOG 的短摘录。Release 表格的来源仓库从锁定清单对应的已核验构建读取。

- `data/sources.lock.json`：本轮订阅构建、版本、样本、源码哈希和收录状态。
