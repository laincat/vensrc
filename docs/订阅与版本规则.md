# 订阅与版本规则

## 安装与更新

将 README 中的主订阅、扩展订阅地址添加到 VeneraX 或 Venera-Next 的漫画源仓库管理。客户端可同时保存多个仓库；索引 URL 是源列表，不是单个 JavaScript 文件。

从订阅仓库安装并保留仓库关联，客户端才能按仓库索引解析固定 Git 提交的下载地址。直接导入、未关联仓库或旧版客户端可能改用源文件自身的 `url`；部分上游将它指向站点首页，届时请从订阅列表重新导入。

## 收录条件

两份订阅均要求同一轮真实通过核心阅读链路：搜索、发现或分类入口至少一项，详情、章节、实际图片下载及解码。主订阅另外要求整次状态为 `passed`；扩展订阅允许核心链路以外的能力失败或受限。

每个源仅抽查固定样本中的一页和一张图片。结果不保证所有漫画、章节、地区、用户账号、设备或 Flutter UI 均可用。跳过、未触发和缺少凭据不会算作通过。

## 上游更新的三条通道

上游发现阶段把每个待审构建归入一条通道。发现阶段只下载文本，读取声明字段和主机名，不加载、不执行。

1. **自动收录**。以下条件全部满足才走这条：
   - 首次出现的 key 可用默认匿名样本（关键词「火影」）参与；不要求旧主机基线。首次收录要排除同名源、已合并的 key 及能识别的同站来源，涉及账号或凭据能力的交人工；
   - 候选的固定提交地址属于 `monitor/upstreams.json` 已登记的仓库；
   - 版本须为三段数字。已有 key 的候选须严格高于清单中同 key 的每个构建；
   - 没有命中官方排除和绅士漫画规则；
   - 对已有 key，静态主机名、两端试跑实际观察到的请求及重定向主机，均与沿用样本的旧构建源码核对。只归一化 `www.`、`m.` 前缀。新增目的地或凭据能力须经人工审阅；
   - 该 key 不是本仓库自建维护的源（清单里指向 `laincat/vensrc` 的构建不自动替换）；
   - 同 key 同时有多个候选时只取版本最高的一个。同版本有多份不同字节时，先取与现有构建同仓库的那份，再看自用仓库优先级；仍分不出唯一一份就不自动收录。

   已有 key 沿用现有样本、设置和预算。新 key 使用默认关键词和空设置，两端须实际读到同一部漫画和章节；首次收录时固定这组样本。发布端还将详情请求的实际站点与现有源对照，同站冲突留给人工复核。同一轮两个客户端均通过 `core()` 后，发布端复核固定源码及试跑记录，再排队入清单。后续升级保留前一版本。
2. **试跑但不收录**。新增网络目的地、凭据能力、同名或同站冲突、版本或证据无法确认的候选进入 [候选短名单](../reports/CANDIDATES.md)。账号凭据只授予 `monitor/accounts.json` 单独审阅并固定的构建 ID。
3. **不执行**。已登记仓库的索引指向未登记仓库的文件时，只在 [上游变更报告](../reports/UPDATES.md) 列出，不下载、不执行。搜索到的新仓库线索同样只列出；其中既没有漫画源索引 `index.json`、也没有 `ComicSource` 脚本的仓库从名单里滤掉，判断不了的照常列出。

源脚本在用户客户端里可能带着登录态运行。源码静态检查与试跑网络记录互补；运行时才生成且本轮未触发的地址仍可能不可见。

### 自动升级后的回退

自动收录的新构建先进入观察期，被它替换的旧构建留在清单里照常巡检，带 `rollbackFor` 标记。订阅对每个 key 仍按原有顺序选一个构建：核心通过 > 整次通过 > 优先级 > 版本。新构建某一轮失败而旧构建仍通过时，订阅在同一轮选回旧构建。

新构建**连续被订阅选中满 7 天且不少于 24 轮**才算稳定，中间有一轮没被选中就重新计数。稳定后旧构建才从清单移除。被重点复测（`monitor/focus.json`）、源备注或账号巡检按构建 ID 引用的旧构建不移除，只去掉回退标记。观察期内删掉旧构建会被清单校验拒绝。

## 官方版本与重复 key

直接来自 `venera-app/venera-configs` 的官方源码默认只作诊断证据。有两种例外会进入订阅：

- **没有社区构建的 key**：官方原版是该 key 唯一可用版本时，按原收录标准参与订阅，不因为来源是官方仓库就被丢弃。
- **沿用官方 key 的社区改版**：仅在版本严格高于官方基线、且自身通过原收录标准时才可收录；同版、低版或版本无法比较都排除。每轮更新基线只增不降，发布前再次核对官方索引。

同一个 key 只要已经有社区构建，官方原版就不再进入订阅（避免同一站点出现两个条目）。上游检测阶段没有社区信息，官方来源的候选一律先排除，只有人工审阅并入清单后才按上面的规则参与订阅。

订阅内部每个 key 只选一个通过门槛的构建，以避免客户端导入和更新冲突。同 key 社区升级源仍可与客户端内置官方源并存，作为替代版本。

## 自建维护的源与巡检工具补丁

有两个源的缺陷无法在上游就地修复（官方仓库没有在响应周期内修、或上游仓库没有许可证、不能把源码复制进本仓库维护分支），因此由本仓库自己实现或适配，清单里指向 `laincat/vensrc` 的固定提交：

- `sources/wnacg.js`（绅士漫画）：只允许本仓库的独立维护版，其他来源的同站源一律不进清单。
- `sources/hot_manga.js`（热辣漫画，1.0.1 起）：官方源 `comic.onClickTag` 对「更新」「状态」两个命名空间直接抛错，用户点标签就报错；本实现只声明可跳转的命名空间（作者、标签），其余命名空间不返回（Venera 约定：不返回=不跳转）。1.0.1 不含账号与收藏能力，因此 `favorites.*` 阶段在巡检中记为跳过，进扩展订阅而不是主订阅。

巡检工具本身也有一处补丁：`patches/venera-patrol-cli-maxpage-null.patch`。上游 `src/validate.js` 只接受非负整数的 `maxPage`，而 VeneraX 的类型注释写明 `Res.subData should be maxPage or null if there is no limit`，`null` 是合法值 —— 包子漫画、Komiic 多账号在「还有下一页」时正是返回 `null`，会被误判成违约。`setup-cli` 在克隆上游后打这个补丁；上游自己放宽后自动跳过（记录为 `upstream`），上游若改了别的实现则直接失败，要求人工复核。

## 同名与同 key 去重

`monitor/catalog.json` 是审阅过的清单，同一站点被不同作者或不同版本重复登记时会累积成多份。每轮巡检前按下面的规则只保留一份，清单因此保持"一个站点一个构建、一个 key 一个构建"：

1. **字节完全相同**：同一源码出现两次（仅仓库不同）只留第一条。
2. **同一个 key**：只保留发布时会被选中的那份。排序与发布一致——今日状态（`passed` > `partial` > 其它）> `priority` > 版本；这个顺序保证删掉的一定是本来就不会进订阅的构建。
3. **不同 key 但同名**：保留排序最高的那个 key，其余同站点的构建合并过去；`KadishJoey/venera-json` 的 `source_xx_hash` 自动导出条目无论排序如何都合并到同名的手写源。

4. **同站不同写法**：名称不同但源码头部请求的是同一个站点域（`www.x.com`、`m.x.com` 视为同站）时，同样只保留排名最高的一份。这条按站点判断而不是按名字，因此能覆盖「漫画柜／漫畫櫃」「X漫画／x漫画-M」这类简繁与移动版命名差异；以下情况不合并，因为它们是不同用途：
   - 多账号版本（`copy_manga_multi_accounts`、`komiic_multi`）：这类版本本身也覆盖单账号用法（主账号走标准登录入口，附属账号可选），因此单账号构建被它取代：`copy_manga` 只保留 `copy_manga_multi_accounts`，`Komiic` 只保留 `komiic_multi`。
   - 私人部署或重制实现（`hj_baozi`、`baozi_recode`）
   - 同域下的分区源（`fourkhd_cosplay` 与 `fourkhd`）
   - 区域／语言版本（`WEBTOON`、`webtoon移动版`、`Webtoon_us`、`LINE WEBTOON`）
   - 源码指向同一域但站点不同的误判（`六漫画` 与 `喵趣漫画` 共用 CDN 域 `bzcdn.net`）

例外一：自动收录观察期内的旧构建（带 `rollbackFor` 标记）在新构建稳定前保留，不按第 2 条删除，见上文「自动升级后的回退」。

例外二：`monitor/focus.json` 里明确列出的重点复测构建即使与同 key 的其他构建重复也保留——重点复测跟踪的是那份固定构建，删掉会让报告失去证据。当前只有 `ccc` 属于这种情况（`zakkida` 的 1.0.2 供重点复测，`handahao666-boop` 的 1.0.1 供订阅）。

被合并的构建不会出现在订阅里，也不会再占用巡检时间；它们的来源和理由记在合并时的提交说明里。

源备注写在索引 `description` 中：一般写 `引用源：owner/repository`；BB-CHICKEN `jm` 使用固定源码提交对应 CHANGELOG 的短摘录。Release 表格的来源仓库从锁定清单对应的已核验构建读取。

## 复核文件

- `monitor/catalog.json`：审阅过的源码、来源仓库、固定样本及 SHA-256；自动收录的条目带 `autoIncluded`。
- `data/pending-updates.json`、[上游变更报告](../reports/UPDATES.md)：全部待审构建及其通道。
- `data/candidate-results.json`、[候选试跑短名单](../reports/CANDIDATES.md)：候选试跑结果。
- `data/auto-inclusion.json`：等待写入清单的队列、观察期内各构建的连续选中轮数。
- `monitor/official-keys.json`、`data/official-exclusions.json`：官方 key、版本基线及索引证据。
- `data/sources.lock.json`：本轮订阅构建、版本、样本、源码哈希和收录状态。
- [双客户端报告](../reports/CLIENT_RESULTS.md) · [订阅清单](../data/sources.zh.csv)。
