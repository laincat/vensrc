# 绅士漫画网页登录与客户端验证

核对日期：2026-10-25（香港时间）。独立源 `wnacg 1.3.4`，来源 `laincat/vensrc`。固定样本 `397513`、关键词“火影”、最低应用版本 `1.3.4` 保留。

## 更正此前结论

1.3.1 的源设置“获取 Cookie”只能读取 App 请求库已经保存的会话；“自动填入”读取剪贴板。这没有完成用户要求的“在 App 网页内完成登录后直接捕获会话”，也没有修复网页滑块被横滑返回抢走的问题。

VeneraX 原版已有 WebView Cookie 自动导入机制，不需要修改客户端即可在源识别到特定私有页后导入 Cookie 并标记登录。新增网页捕获按钮、关闭抢先触发的返回手势，以及等待 App 请求核验完成后再接受登录，才需要修改客户端。本项目当前按“不修改 VeneraX”推进，只使用原版支持的私有页触发方案。

核对 `Gandum2077/venera-configs` 的 `ai` 分支、提交 `cbde997745bb9891d2c53ae1c1265f34ba562384`（2026-10-24，`wnacg 1.0.12`）：

## 1.3.4：识别“我的书架”账户页

用户于 2026-10-25 提供的 VeneraX 请求诊断显示：App 对 `www.wnacg.com/users-users_fav.html` 发送了已脱敏的 Cookie；服务器返回 HTTP 200，页面标题为“我的書架-紳士漫畫移動版”。源先前只接受指定 `/users-logout.html` 链接，网页登录标题也只允许“我的空间”，因此把此账户页判成未登录。所给响应是站点 HTML，不是 403 或 CF 挑战响应。

1.3.4 在站点和账户页 URL 已匹配、页面无权限提示的前提下，也接受该站实际返回的“我的书架／我的書架”标题；WebView 成功页识别同步加入该标题。若页面含“您沒有權限／需要登錄”等提示，仍拒绝登录，即使 HTTP 为 200、标题像书架。Cookie 内容不需要、也不应提供给巡检或报告。

`BB-CHICKEN/venera-jm 1.9.2` 使用 JM 的 `/login` API，收到有效 `uid` 后登录；它没有 WebView 捕获或滑块手势处理。其会话管理可参考，但网络异常／5xx 返回 `true` 不能当作本次登录已验证。

## 原版客户端的登录路径

| 路径 | 操作和状态 | 仍需验证 |
| --- | --- | --- |
| 原版 VeneraX／Venera-Next | 本人在 App 内网页登录、完成滑块，然后点站点内“我的收藏”。匹配真实私有页后，由客户端导入 Cookie，源保存原登录域名 | 这是 `browser_only`；App 读取收藏前还会请求会员页校验。按钮和横滑冲突没有因此得到修复 |

此路径不要求从外部浏览器复制 Cookie。原版的触发操作是**网页内的“我的收藏”**，不要在未触发时直接点 App 左上角返回；普通返回不会同步会话。

本次重新读取站点公开登录表单及 `common.js`：表单没有已确认的登录后跳转字段，成功后的页面行为依赖服务器返回内容。没有证据支持随意添加 `redirect`／`return_url` 参数；源的回调也没有 WebView 控制器可用于强制跳转。因此仍保留站内“我的收藏”触发，不把自动跳转到该页写成已经实现的功能。

`webLoginVerification` 单独记录：

- `browser_only`：私有页识别与 Cookie 导入完成，未冒充 App HTTP 权限验证。
- `http_verified`：App 请求 `users-users_fav.html`，确认本站账户页标志（退出链接或已知“我的书架”标题）、无权限提示、无 CF 挑战后才记录。

在 VeneraX 原版中，客户端先把 WebView Cookie 写入 App CookieJar，再调用源的同步成功回调，随后将账号标记为已登录。源无法控制这一原生导入时机，也不能自行添加 WebView 按钮或关闭 App 的返回手势。缺 Cookie、登录页、匿名页、5xx、网络故障或挑战页都不能作为新的服务端登录验证成功。

源设置中的 Cookie 导出和剪贴板导入保留为手动后备，不再把它们描述为网页内捕获。Cookie 不回显、不上传到 Actions 或报告。

## 1.3.3：返回 App 后的只读实测入口

用户反馈：站内打开“我的收藏”后自动返回 App，出现“注销”入口。它符合原版完成导入后设置本地 `account` 标记的流程，但不能单凭此现象确认站点接受 App 的会员请求，也不能证明所有漫画页面正常。

新增两项源端提示，不修改 VeneraX：

1. 原版成功回调在检查到 App CookieJar 的 Cookie 后显示“App 已接收网页 Cookie”，同时说明会员权限尚未验证。
2. 在已安装的漫画源列表中展开**“紳士漫畫”卡片**，确认版本为 `1.3.4`，点击设置项里的**“检查登录与浏览”**。它显示本地登录标记、会话域名、阅读域名、适用于会员页的 Cookie 数量，以及本次 App 请求的会员页、首页解析、固定漫画详情 `397513` 的结果。Cookie 名称、值、异常原文和漫画内容均不显示；不下载图片，不修改收藏。

这项检查在用户当前 App 内运行，使用客户端自己的 HTTP 和 HTML 接口，可以在正常返回后执行一次，再完整关闭并重开 App 后执行一次。两次都确认 Cookie 存在且会员页通过，才能确认当前设备的会话保留和站点接受情况。当前电脑没有该 App 或设备镜像，尚未得到这两次实机结果；CLI 或构造响应测试不能替代它们。

| 对话框结果 | 可以判断的范围 |
| --- | --- |
| 本地标记已设置，但 Cookie 为 0 或会员页未通过 | 不能把“可注销”算成服务端登录通过；继续核对域名、Cookie、权限及网络 |
| 会员页通过，首页或固定详情出现 HTTP／源解析错误 | 本次会话可用于会员页；浏览故障需继续核对对应请求或页面解析 |
| 会员页、首页和固定详情均通过，但图片仍不能打开 | 图片下载和 CDN 尚未验证，不能依据页面通过而宣称完整阅读通过 |
| 阅读与登录域名不同 | 阅读仍使用所选备用地址，主域 Cookie 不会跨域复制 |

同时修正一个与原版客户端接口有关的源端隐患：VeneraX 的共享网络缓存可返回字节正文，旧源直接按字符串处理。1.3.3 对所有 HTML GET 统一做 UTF-8 转换，并让会员页面绕过缓存；这与 Gandum2077 的 `responseText` 处理思路一致。1.3.4 的测试继续用两套客户端原始 JavaScript bootstrap 验证字节解码，并覆盖“我的書架”标题及携带权限提示时的拒绝路径。

## 客户端补丁与证据边界

本项目只维护漫画源和订阅，不修改或构建 VeneraX。源代码可核对 App 请求的会员页、首页与固定漫画详情；网页登录滑块及重启后的会话保留，仍以用户设备上的实际结果为准，不能用 CLI 测试代替。

## 发布页和备用地址

- 内置 `www.wnacg.com`、`www.wnacg.ru`；发布页曾公布 `www.wn003.cfd`、`www.wn004.cfd`。
- 使用 `wnacg01.link` 和 `wnacg02.link`，距上次成功同步满 24 小时再刷新；设置页也可手动刷新。
- 只收录受限域名格式的 HTTPS 漫画地址；失败保留缓存，不把广告或发布页当漫画服务器。
- 切换阅读地址不搬运 Cookie；账号请求通过 `accountBaseUrl` 留在实际登录域名。登录标记清除后需重新确认会话。
- 发布页列出、浏览器能打开和登录交互模块存在均不等于可用性通过。访问结果见 [访问报告](ACCESS_RESULTS.md)。
