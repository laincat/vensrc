## 1.2.0 添加失败修复

VeneraX 截图中的 `Null check operator used on a null value` 对应原生 `js_engine.dart:180` 的 `ComicSource.find(key)!`。原生解析器先读取账号配置，再构造、注册源；1.2.0 的账号 getter 为拼接 WebView 地址调用 `loadSetting`，发生在原生源注册之前。之前 CLI 仅注册了 JS 实例就读取配置，没有覆盖这一步原生导入顺序，导致漏检。

本版将 WebView 入口固定为 `https://www.wnacg.com/users-login.html`，导入时不读取源设置；实际阅读、Cookie 校验和导出时仍使用选定域名。App 内网页登录请选 `www.wnacg.com`；其他地址保留手动 Cookie 登录。两个客户端的桥接测试新增账号配置解析阶段：用旧调用重现并拒绝错误，再加载修复后的实际源。该回归测试纳入每日 Actions；它验证接口及导入顺序，不能替代手机实机验证。

## 登录失败的实际原因

`www.wnacg.com` 与 `www.wnacg.ru` 的公开登录页加载站点自建的 `slider-captcha.js`。脚本注明该流程于 2026-10-23 加入：本人完成滑块后，表单才附带一次性 `slider_pass` 提交。旧源直接提交用户名和密码，没有该流程，因此不能据失败判断密码错误，也不能直接归因为 Cloudflare。

公开登录页及脚本使用不含账号的 GET 请求核对。页面中的 Cloudflare 统计脚本不等于 CF 挑战；以真实挑战响应判断 CF。发布页为 `https://wnacg01.link/`。

## 独立源的处理

- 阅读、分类、章节、缩略图和收藏解析基于官方 1.0.6 保留；不再提供旧密码直登。
- App 内网页登录固定打开 `www.wnacg.com/users-login.html`。本人完成站点滑块并进入会员页后，源会立即请求 `/users-index.html` 核对退出链接和权限提示，通过后自动保存登录状态；仅 URL 变化、登录页、权限提示、普通首页和 CF 挑战都不算成功。
- 设置页提供两个独立按钮。“获取 Cookie”读取 App 当前域名 Cookie，先验证会员会话，再把 Cookie 请求行复制到剪贴板；“自动填入”读取剪贴板中的一行 Cookie 请求头，验证会员页后直接保存登录状态并清空剪贴板，不需要手工粘贴到账号表单。界面和报告均不回显 Cookie。
- 手动 `account.loginWithCookies.validate` 仍保留，作为网页登录不可用时的后备方式。
- 访问域名只允许内置地址及从发布页同步的受限域名格式，默认 `www.wnacg.com`，避免任意域名接收会话。
- 本人在正常浏览器完成站点滑块，再把该域名的 Cookie 填入客户端；源只向相同域名导入会话。
- 验证请求为 `/users-index.html`。HTTP 200 不足以证明登录：必须找到会员页的本站退出登录链接，且没有未登录权限提示。匿名首页、普通登录页、CF 挑战和请求失败均不通过；失败会恢复之前的 Cookie。
- 不保存或输出账号密码，不代解滑块，不生成验证票据。本站密码 Secret 保留在 GitHub 设置中，但工作流已停止注入。

之前 5 个绅士漫画构建已从审阅清单移除：Taototo 私人版、KadishJoey 国内直连版和另一替代版、官方 1.0.6、yelongyue197-svg 1.0.5。发现、清单校验及 Release 校验均只接受本仓库的独立版，其他来源不能重新进入订阅。

## 客户端使用

1. 刷新来源库中的 Vensrc-Ext，确认显示 `紳士漫畫 1.3.1` 后再添加或更新。已经安装同 key 源时应选择更新；无需清空客户端或其他来源库。之前安装的不同 key 旧版需要手动移除。
2. 在源详情页的“设置”中点击“获取 Cookie”或“自动填入”。这两个按钮不在账号登录弹窗内；客户端接口不允许源往原生登录表单注入按钮或文本。
3. 推荐先点账号区的网页登录，由本人完成登录和站点滑块并进入会员页。成功返回后，源会自动验证并保存会话；如需迁移到其他同域客户端，再点“获取 Cookie”复制当前会话。
4. 从浏览器复制一行 `Cookie` 后，直接点“自动填入”。源会导入当前所选域名、验证会员页，成功才登录并清空剪贴板；失败会恢复旧 Cookie。切换域名或会话过期后需重新登录。

Cookie 等同于登录凭据，只在本人设备和客户端中处理。不要贴到 issue、Actions Secrets、报告或聊天中。已有浏览器完成 CF 验证的会话也可能绑定网络、设备或 User-Agent；导入后仍被要求验证时，源会报错，不能保证 Cookie 可跨环境通用。

## 两个客户端与 CLI 的边界

| 环境 | 接口与结果边界 |
| --- | --- |
| VeneraX 2.3.6 | 支持设置回调、网页登录、Cookie 导入和异步 Cookie 校验；网页登录以会员中心 URL 与标题双重判断 |
| Venera-Next 1.18.0 | 同样支持上述接口；使用相同源码和样本独立复测 |
| 最新 venera-patrol-cli | 可调用 Cookie 校验接口；没有本人浏览器会话时，记为 `credentials_missing`／跳过，不能记为登录通过 |
| GitHub Actions | 不接收绅士漫画密码或浏览器 Cookie；两个客户端均测试缺凭据处理，匿名阅读链路另行判断 |

上述客户端版本指 `monitor/clients.json` 中固定、已核验源码哈希的接口版本。两个客户端都会把 WebView 的 Cookie 保存到源共享会话；VeneraX 的成功回调不等待异步结果，Venera-Next 会等待，因此网页登录的 `checkStatus` 保持同步，不使用异步回调冒充登录成功。Cookie 按钮会再用真实会员页验证，属于用户主动操作。

本地测试只使用明确标记的测试数据验证接口和失败保护。真实账号 Cookie 尚未在本人设备导入验证，不能宣称账号已经登录成功。当次双客户端阅读结果见 [客户端结果](CLIENT_RESULTS.md)，云端登录状态见 [账号结果](ACCOUNT_RESULTS.md)；只有同轮阅读链路满足门槛才进入订阅。
